## ۱. چکیدهٔ اجرایی و مرز اثر

Mojavez-v2 یک سامانهٔ مدیریت مجوز صنایع دستی است که با PHP ۸ خالص (بدون فریم‌ورک و بدون Composer)، معماری MVC دست‌نویس و MySQL/MariaDB پیاده‌سازی شده است. پروژه یک گذار refactor کامل از نسخهٔ v0.7.2 قبلی را پشت سر گذاشته (۴۵ یافته، ۱۳ مورد HIGH) و به ادعای `REFACTOR_PLAN.md` به نسخهٔ v2.0.0 رسیده است. با این حال، تحلیل ساختاری نشان می‌دهد که پروژه برای پذیرش یک ماژول یکپارچه‌سازی خارجی مانند mojavez-gateway آماده نیست: ده حوزهٔ ساختاری اصلی (لایهٔ ماژولار، API، احراز هویت API، رویداد، صف، لایهٔ دسترسی به داده، runner مهاجرت، CI/CD، وابستگی‌ها و لاگ‌گذاری) نیازمند توسعه است.

این سند بر فرض برنامهٔ توسعه‌دهنده بنا شده است: «ابتدا Mojavez-v2 به‌طور کامل توسعه می‌یابد، سپس با mojavez-gateway در یک مخزن جدید یکپارچه می‌شود». تحلیل نشان می‌دهد که این ترتیب درست است، اما «توسعهٔ کامل» باید شامل شش فاز زیرساختی باشد که در غیاب آن‌ها، یکپارچه‌سازی به debt فنی سنگین، ریسک‌های امنیتی و lock-in داده‌ای منجر می‌شود. بخش مرکزی این سند (بخش ۵) به دوازده جنبهٔ پنهان می‌پردازد که در آیندهٔ یکپارچه‌سازی ممکن است آشکار شوند: از drift همگام‌سازی دوطرفه و race condition تا مالکیت دادهٔ PII پس از قطع gateway.

**مرز اثر:** این سند تحلیلی است و هیچ تغییری در مخزن اعمال نمی‌کند. به‌دلیل خصوصی بودن mojavez-gateway، تحلیل یکپارچه‌سازی بر الگوهای عمومی و قرینه‌سازی با ماژول Scraper نسخهٔ محلی استوار است؛ هر فرض به‌صراحت علامت‌گذاری شده است.

## ۲. زمینه: وضعیت فعلی Mojavez-v2

### ۲.۱. هویت پروژه و معماری

Mojavez-v2 سامانه‌ای تحت وب برای مدیریت کامل فرآیند درخواست مجوز صنایع دستی است: از ثبت‌نام چندمرحله‌ای متقاضی و بارگذاری مدارک تا پیگیری با کد رهگیری (`HG-XXXXXXXX`)، پنل مدیریت نقش‌محور (admin/expert/document_uploader)، لغو خودکار درخواست‌های منقضی و گزارش‌گیری Excel/چاپی. پشتهٔ فنی شامل PHP ۸ خالص بدون فریم‌ورک و بدون Composer، معماری MVC دست‌نویس با `core/AutoLoader.php`، MySQL/MariaDB با PDO و Prepared Statements، Bootstrap ۵ RTL محلی و فونت وزیرمتن است. ساختار مخزن شامل ۲۳ کنترلر، ۲۸ مدل، ۵ سرویس (`ApplicantRegistrationService`, `AutoCancelService`, `FeeCalculatorService`, `FileStorage`, `PaymentReceiptService`) و ۲۸ جدول در `database/schema.sql` است.

### ۲.۲. تاریخچهٔ refactor

بر اساس `REFACTOR_PLAN.md`، این مخزن از `andrbi109/Mojavez` در کامیت `ad133b5 v0.7.2` کلون شده و یک refactor کامل ۱۳-فازی روی آن اجرا شده است. خروجی‌ها شامل رفع ۱۳ مورد HIGH (مانند انتقال `APP_DEBUG` و اعتبارنامهٔ DB به `.env`، rate limit روی `/tracking/print` و `/license/view/{token}`، محافظت `/check-cancel` با `CRON_SECRET`)، کاهش ۸۵۰ خط کد تکراری، استخراج دو سرویس متمرکز (`ApplicantRegistrationService` ۴۷۸ خط و `PaymentReceiptService` ۲۳۶ خط)، یک مدل مرجع (`DocTypes`) و یک مهاجرت idempotent (`20251109_v2_upgrade.sql`) بوده است. این refactor بنیان خوبی فراهم کرده، اما روی یکپارچه‌سازی خارجی متمرکز نبوده است.

### ۲.۳. سه‌گانگی نسخه — نشانهٔ عدم بلوغ release

یافتهٔ نگران‌کننده: سه منبع مختلف سه نسخهٔ متفاوت گزارش می‌دهند. `README.md` خط ۵ اعلام می‌کند «نسخهٔ ۰.۱.۰ — اولین نسخهٔ رسمی»؛ فایل `VERSION` حاوی `0.6.3` است؛ و `REFACTOR_PLAN.md` خط ۱۲۱ اعلام می‌کند «نسخهٔ نهایی: v2.0.0». این تناقض نشان می‌دهد که فرآیند release نسخه‌بندی یکپارچه ندارد: `README` قدیمی است، `VERSION` با واقعیت کد هم‌خوان نیست، و فقط `REFACTOR_PLAN` به v2.0.0 ارجاع می‌دهد. برای یک پروژه‌ای که قرار است با یک ماژول خارجی یکپارچه شود و قرارداد نسخه‌دار نیاز است، این سه‌گانگی خطرناک است: هیچ منبع حقیقت واحدی برای نسخهٔ schema، نسخهٔ API یا نسخهٔ قرارداد یکپارچه‌سازی وجود ندارد.

## ۳. کمبودهای ساختاری (ده حوزه)

ده حوزهٔ ساختاری زیر، پیش‌نیاز یکپارچه‌سازی با gateway هستند و در وضعیت فعلی ناقص یا غایب‌اند.

### ۳.۱. نبود لایهٔ ماژولار

بررسی ساختار `app/` نشان می‌دهد که دایرکتوری `app/Modules/` وجود ندارد. پروژه به‌جای معماری ماژولار، کنترلرها/مدل‌ها/سرویس‌ها را به‌صورت مسطح در `app/Controllers`, `app/Models`, `app/Services` نگه می‌دارد. این یعنی هیچ مکانیزمی برای بارگذاری یک ماژول خارجی (مثل gateway) به‌صورت ایزوله وجود ندارد: gateway باید یا در همان ساختار مسطح ادغام شود (که قبضهٔ کد را بالا می‌برد) یا به‌صورت یک لایهٔ جداگانه با loader سفارشی پیاده‌سازی شود. نبود `ModuleInterface` و `ModuleLoader` به‌معنای آن است که هر ماژول جدید باید به‌صورت موردی و غیراستاندارد متصل شود. این بزرگ‌ترین مانع معماری برای یکپارچه‌سازی است.

### ۳.۲. نبود لایهٔ API

تحلیل `core/Router.php` نشان می‌دهد که روتر فقط `GET` و `POST` را پشتیبانی می‌کند، بدون middleware، بدون گروه‌بندی مسیرها و بدون مذاکرهٔ `Content-Type`. جستجو در `app/` و `core/` نشان می‌دهد که فقط ۷ فایل از `json_encode` استفاده می‌کنند و فقط ۲ فایل `application/json` تنظیم می‌کنند — و **همهٔ کاربردهای `application/json` در `FeeTariffController.php` متمرکزند** (پاسخ‌های AJAX پنل مدیریت). هیچ REST API عمومی، هیچ کنترلر منبع API، هیچ نسخه‌بندی مسیر (`/api/v1/`) و هیچ قرارداد خروجی JSON استاندارد وجود ندارد. gateway برای همگام‌سازی داده به یک API مصرفی نیاز دارد؛ این لایه باید از صفر ساخته شود.

### ۳.۳. نبود احراز هویت API

جستجوی `api_key`, `Bearer`, `api_token`, `API_KEY` در `app/`, `core/`, `config/` **صفر نتیجه** داد. سامانه فقط احراز هویت مبتنی بر نشست (session) برای پنل مدیریت دارد (`AuthController` + `Session`). برای یکپارچه‌سازی خارجی، gateway نمی‌تواند نشست برقرار کند؛ به یک مکانیزم احراز هویت stateless نیاز است: API key، OAuth2 client-credentials یا JWT. نبود این لایه به‌معنای آن است که هر endpoint API که برای gateway ساخته شود، در معرض دسترسی عمومی خواهد بود مگر اینکه یک لایهٔ احراز هویت جداگانه ساخته شود.

### ۳.۴. نبود سیستم رویداد و webhook

جستجوی `dispatch`, `event`, `webhook`, `queue`, `async` در `app/` و `core/` فقط به `Router::dispatch` (که متد مسیریابی است، نه event dispatcher) و نماهای HTML (attributeهای `onclick`) می‌رسد. هیچ event dispatcher واقعی، هیچ webhook خروجی و هیچ مکانیزم pub/sub وجود ندارد. این یعنی gateway نمی‌تواند به‌صورت reactive به تغییرات (مانند «مجوز صادر شد» یا «پرداخت تأیید شد») واکنش نشان دهد؛ باید به polling متوسل شود. نبود webhook خروجی همچنین به‌معنای آن است که هیچ راه استانداردی برای اطلاع‌رسانی رویدادها به gateway وجود ندارد.

### ۳.۵. نبود صف و غیرهمزمانی

`AutoCancelService` در هر بازدید از صفحات کلیدی (داشبورد، پیگیری) یا فراخوانی `GET /check-cancel` به‌صورت **هم‌زمان** اجرا می‌شود. این الگو برای یک عملیات سبک (لغو درخواست‌های منقضی) قابل‌قبول است، اما برای همگام‌سازی gateway (که شامل فراخوانی شبکه، scraping یا API خارجی است) فاجعه‌بار خواهد بود: یک فراخوانی gateway کند، زمان بارگذاری صفحهٔ کاربر را چند برابر می‌کند. نبود صف (queue) و worker غیرهم‌زمان به‌معنای آن است که هر همگام‌سازی gateway یا هم‌زمان و مسدودکننده است یا باید به cron job خارجی متوسل شود.

### ۳.۶. نبود لایهٔ دسترسی به داده

مدل‌ها (مانند `Applicant.php`, `Person.php`) مستقیماً با `Database::getInstance()->getConnection()` و کوئری‌های PDO خام کار می‌کنند و الگوی `SELECT *` را به‌کار می‌برند. هیچ الگوی Repository، هیچ Interface داده‌ای و هیچ لایهٔ انتزاع وجود ندارد. این امر دو پیامد دارد: نخست، gateway نمی‌تواند داده را از یک منبع انتزاعی بخواند (مستقیماً به مدل‌های concreto وصل می‌شود)؛ دوم، تست‌پذیری کاهش می‌یابد (مدل‌ها بدون DB واقعی قابل mock نیستند). برای یکپارچه‌سازی پایدار، یک لایهٔ Repository با Interface مورد نیاز است تا gateway از طریق قرارداد داده دسترسی داشته باشد، نه از طریق پیاده‌سازی مدل.

### ۳.۷. نبود زیرساخت مهاجرت

شش فایل مهاجرت در `database/migrations/` وجود دارند (از `20251109_v2_upgrade.sql` تا `20251114_migrate_documents_to_tracking_code_folders.sql`) اما **هیچ runner مهاجرتی و هیچ جدول `migrations` برای پیگیری نسخه وجود ندارد**. مهاجرت‌ها دستی، idempotent و در `schema.sql` بازپخته شده‌اند. نگران‌کننده‌تر: **دو فایل schema موازی** وجود دارد — `database/schema.sql` (۱۱۷۹ خط) و `database/install.sql` (۱۲۷۹ خط) — که هر دو ۲۸ جدول دارند اما خطوط متفاوتی (۱۰۰ خط اختلاف). این drift به‌معنای آن است که منبع حقیقت schema واحد نیست و نصب‌های جدید ممکن است با نصب‌های ارتقایافته تفاوت داشته باشند. برای یکپارچه‌سازی gateway (که جدول‌های جدید و FK مشترک می‌افزاید)، نبود runner و drift schema خطر جدی است.

### ۳.۸. نبود CI/CD و آزمون یکپارچه‌سازی

هیچ دایرکتوری `.github/workflows/` وجود ندارد. آزمون‌ها (`tests/`) شامل `smoke-test.sh`, `FunctionalTest.php`, `SecurityTest.php` و چند آزمون تخصصی‌اند، اما همهٔ آن‌ها دستی و با `php tests/run.php` اجرا می‌شوند. هیچ pipeline خودکار برای آزمون، lint یا deploy وجود ندارد. برای یکپارچه‌سازی gateway، آزمون یکپارچه‌سازی (contract test) حیاتی است: باید تأیید کرد که قرارداد بین v2 و gateway پس از هر تغییر حفظ می‌شود. بدون CI/CD، هر تغییر به‌صورت دستی آزمون می‌شود و regressions به تولید می‌رسد.

### ۳.۹. نبود Composer و autoloading استاندارد

هیچ `composer.json` وجود ندارد. پروژه از `core/AutoLoader.php` سفارشی استفاده می‌کند. این انتخاب آگاهانه (بدون وابستگی خارجی) برای یک پروژهٔ تک‌هدفی قابل‌احترام است، اما برای یکپارچه‌سازی gateway محدودیت ایجاد می‌کند: gateway ممکن است وابستگی‌های خود را داشته باشد (HTTP client, queue library) که بدون Composer باید دستی کپی شوند. همچنین نبود PSR-4 به‌معنای آن است که قرارداد فضای نام ماژول‌ها غیراستاندارد است و بارگذاری ماژول خارجی نیازمند منطق سفارشی است.

### ۳.۱۰. نبود لاگ‌گذاری ساختاریافته و نظارت

`public/index.php` از `error_log` بومی PHP و `ERROR_LOG_PATH` استفاده می‌کند، اما هیچ لاگ‌گذاری ساختاریافته (structured logging با زمینه و سطح) و هیچ متریک (metrics) وجود ندارد. برای یکپارچه‌سازی gateway، نظارت حیاتی است: باید مشخص کرد کدام همگام‌سازی‌ها شکست خورده، چه حجم داده‌ای جابجا شده و چه تأخیری وجود دارد. نبود لاگ ساختاریافته به‌معنای آن است که یک نقص همگام‌سازی gateway در لاگ‌های پر‌سر‌و‌صدا گم می‌شود و تشخیص ریشه‌ای دشوار است.

## ۴. نقص‌های داده‌ای و یکپارچگی

### ۴.۱. applicants به‌عنوان cascade hub

جدول `applicants` مرکز وابستگی است: ۱۲ جدول با `ON DELETE CASCADE` به آن ارجاع می‌دهند (`job_details`, `property_details`, `documents`, `status_log`, `postal_code_changes`, `applicant_field_values`, `license_access_requests`, `payments`, `license_files`, `user_sms_entries`, `applicant_revisions`, `user_notifications`) و دو ارجاع `SET NULL` (`persons`, `service_types`). هر عملیات تخریبی روی `applicants` (drop/recreate، تغییر PK) به ۱۲ جدول سرایت می‌کند و دادهٔ تاریخی را نابود می‌سازد. gateway اگر بخواهد دادهٔ متقاضی را همگام کند، مستقیماً به `applicants` وابسته می‌شود؛ هر تغییر schema در `applicants` هم بر gateway و هم بر ۱۲ جدول فرزند اثر می‌گذارد.

### ۴.۲. ۱۸ ستون ENUM در ۱۲ جدول

پرخطرترین نوع ALTER در MySQL، تغییر ENUM است. schema دارای ۱۸ ستون ENUM در ۱۲ جدول است، از جمله `applicants.current_status` با ۱۸ مقدار فارسی، `applicants.applicant_type`, `payments.status`, `payments.purpose` و غیره. `current_status` قبلاً یک‌بار در مهاجرت `20251111_household_status_enum.sql` تغییر کرده (افزودن وضعیت‌های مشاغل خانگی). gateway اگر وضعیت‌های جدیدی تولید کند (مانند «در حال همگام‌سازی با پورتال» یا «صادرشده در پورتال خارجی»)، باید به ENUM افزوده شود؛ تغییر مقدار موجود در ENUM بازسازی جدول + تغییر همهٔ literalهای hardcoded در مدل‌ها و کنترلرها را الزامی می‌کند.

### ۴.۳. نبود جدول audit/integration log و idempotency key

هیچ جدولی برای ثبت رویدادهای یکپارچه‌سازی (کدام رکورد، کِی، با چه نتیجه‌ای همگام شد) وجود ندارد. `payment_audit_log` وجود دارد اما مختص پرداخت است. برای یکپارچه‌سازی gateway، یک جدول `integration_log` (با `entity_type`, `entity_id`, `direction`, `status`, `gateway_ref`, `payload_hash`, `synced_at`) و یک ستون `idempotency_key` روی جداول همگام‌شده ضروری است. نبود این‌ها به‌معنای آن است که همگام‌سازی تکراری (مثلاً پس از timeout + retry) به رکورد تکراری منجر می‌شود و قابل تشخیص نیست.

### ۴.۴. نبود soft-delete و دادهٔ زمان‌مند

جداول از hard-delete (`ON DELETE CASCADE`) استفاده می‌کنند. هیچ ستون `deleted_at` و هیچ مکانیزم soft-delete وجود ندارد. برای یکپارچه‌سازی gateway، این خطرناک است: اگر gateway یک رکورد را حذف کند (یا همگام‌سازی حذف را انتقال دهد)، دادهٔ v2 برای همیشه از بین می‌رود و بازگردانی ممکن نیست. همچنین نبود دادهٔ زمان‌مند (temporal data با `valid_from`/`valid_to`) به‌معنای آن است که تاریخچهٔ تغییرات وضعیت فقط در `status_log` دیده می‌شود، نه در خود رکورد.

## ۵. جوانب پنهان برای آینده (بخش مرکزی)

این بخش به جنبه‌هایی می‌پردازد که در فاز طراحی یکپارچه‌سازی معمولاً پنهان می‌مانند اما در تولید آشکار می‌شوند و پرهزینه می‌شوند.

### ۵.۱. drift همگام‌سازی دوطرفه

وقتی v2 و gateway هر دو روی یک موجودیت (مثلاً وضعیت درخواست) نوشتن می‌کنند، drift اجتناب‌ناپذیر است: کاربر در v2 وضعیت را به «تأیید نهایی» تغییر می‌دهد، هم‌زمان gateway از پورتال خارجی وضعیت «در حال بررسی» را می‌خواند و بازنویسی می‌کند. بدون یک قاعدهٔ حل تعارض (last-write-wins با timestamp، یا source-of-truth مشخص برای هر فیلد)، داده به‌سرعت ناسازگار می‌شود. **پنهان:** این drift در آزمون یکپارچه‌سازی ظاهر نمی‌شود چون آزمون‌ها هم‌زمانی واقعی تولید نمی‌کنند؛ فقط در تولید با کاربر هم‌زمان آشکار می‌شود.

### ۵.۲. race condition و retry تکراری

 gateway timeout می‌شود، retry می‌کند، هم‌زمان v2 هم‌زمان یک به‌روزرسانی دریافت می‌کند. بدون idempotency key (بخش ۴.۳)، retry به رکورد تکراری یا به‌روزرسانی اشتباه منجر می‌شود. حتی با idempotency key، race condition بین دو فراخوانی هم‌زمان gateway نیاز به قفل (row lock یا optimistic concurrency با `version`) دارد. **پنهان:** بدون بار ترافیکی واقعی قابل تشخیص نیست؛ در تولید با هم‌زمانی بالا ظاهر می‌شود.

### ۵.۳. version mismatch و contract drift

 gateway به‌سرعت تکامل می‌یابد (نسخهٔ قرارداد ۱ → ۲)، اما v2 ممکن است هنوز روی نسخهٔ ۱ باشد. بدون نسخه‌بندی قرارداد (مثلاً `X-Contract-Version` header یا URL `/api/v1/`) و بدون schema registry، یک تغییر در gateway می‌تواند v2 را بشکند. **پنهان:** regressions آهسته ظاهر می‌شوند — gateway به‌روزرسانی می‌شود، v2 تا هفته‌ها کار می‌کند، سپس یک endpoint خاص می‌شکند.

### ۵.۴. lock-in داده‌ای و رکورد یتیم

پس از ماه‌ها همگام‌سازی، دادهٔ v2 با `gateway_ref` پر شده است. اگر gateway قطع شود یا لغو شود، این رکوردها «یتیم» می‌شوند: `gateway_ref` به موجودیتی اشاره می‌کند که دیگر وجود ندارد. **پنهان:** این مشکل در زمان قطع فوری نیست؛ در زمانی که تصمیم به جایگزینی gateway گرفته می‌شود آشکار می‌شود و هزینهٔ پاک‌سازی بالاست. باید ستون `gateway_ref` nullable + قابل null-shifting باشد و یک سیاست «forget» برای gateway وجود داشته باشد.

### ۵.۵. API endpoint به‌عنوان سطح حملهٔ جدید

هر endpoint API که برای gateway ساخته می‌شود، یک سطح حملهٔ جدید است. بدون rate limit سراسری، بدون اعتبارسنجی ورودی متمرکز، بدون schema validation و بدون audit log، یک endpoint نشت‌یافته می‌تواند کل دادهٔ PII متقاضیان را افشا کند. **پنهان:** خطر در خود endpoint نیست، در مکانیزم احراز هویت است: یک API key نشت‌یافته (در لاگ، در git history، در شبکه) به کل سیستم دسترسی می‌دهد. باید scope-based authorization (هر key فقط به منابع خاص) داشته باشد.

### ۵.۶. بازیابی فاجعه و circuit breaker

 gateway قطع می‌شود (سرور خارجی از کار می‌افتد، شبکه قطع می‌شود). بدون circuit breaker، v2 به‌طور بی‌وقفه retry می‌کند، صف پر می‌شود، دیسک پر می‌شود و v2 خودش از کار می‌افتد. **پنهان:** بدون circuit breaker، قطع gateway به قطع v2 منجر می‌شود — یک شکست موضعی به فاجعهٔ سراسری تبدیل می‌شود. باید v2 بتواند بدون gateway کار کند (degraded mode) و همگام‌سازی معلق در صف بماند تا gateway برگردد.

### ۵.۷. drift schema در مخزن جدید

وقتی در یک مخزن جدید ادغام می‌شوند، چه کسی مالک schema است؟ اگر هر دو تیم schema را تغییر دهند، drift ایجاد می‌شود. **پنهان:** بدون ماتریس مالکیت روشن (چه جدولی متعلق به کدام ماژول است) و بدون shared kernel مشخص، تغییرات هم‌زمان در دو ماژول به conflicting FK یا نوع‌های ناسازگار منجر می‌شود.

### ۵.۸. نبود قرارداد تست (contract test)

بدون contract test، هر تغییر در v2 می‌تواند gateway را بشکند و برعکس. contract test‌ها قرارداد را به‌صورت اجرایی ثبت می‌کنند: اگر v2 پاسخ `/api/v1/applicants/{id}` را تغییر دهد، تست gateway fail می‌شود. **پنهان:** نبود contract test به‌معنای آن است که یکپارچه‌سازی فقط در زمان deploy آزمون می‌شود — یعنی در تولید.

### ۵.۹. مالکیت داده و حریم خصوصی

 gateway به PII متقاضیان (کد ملی، موبایل، آدرس) دسترسی پیدا می‌کند. اگر gateway در یک حوزهٔ قضایی دیگر میزبانی شود، انتقال PII ممکن است نیازمند رضایت صریح کاربر یا انطباق با قوانین حفاظت از داده باشد. **پنهان:** این مشکل فنی نیست، حقوقی است؛ اما در زمان ممیزی یا شکایت کاربر آشکار می‌شود. باید minimum-necessary principle (فقط دادهٔ لازم به gateway برود) و audit log دسترسی ثبت شود.

### ۵.۱۰. debt فنی پس از refactor

refactor v2.0.0 چهارده مورد HIGH را رفع کرد، اما توسعهٔ شش فاز زیرساختی (بخش ۷) debt جدید وارد می‌کند: ماژولار کردن، API، احراز هویت، رویداد، صف، repository. اگر این فازها بدون نظم اجرا شوند، debt انباشته می‌شود و خود به یک refactor دیگر نیاز می‌شود. **پنهان:** refactor بدون نظم، به‌جای کاهش debt، آن را جابجا می‌کند؛ یکپارچه‌سازی با debt بالا، ریسک بالاتری از شکست دارد.

### ۵.۱۱. تکامل موازی و merge conflict فرهنگی

وقتی v2 و gateway هر دو به‌طور موازی توسعه می‌یابند (تیم‌های مختلف یا حتی همان توسعه‌دهنده با اولویت‌های مختلف)، سبک کد، قراردادها و اولویت‌ها واگرا می‌شوند. **پنهان:** این drift فرهنگی در کد دیده نمی‌شود، اما در زمان ادغام به conflict‌های طراحی تبدیل می‌شود. یک سند قرارداد مشترک + مالکیت روشن این را کاهش می‌دهد.

### ۵.۱۲. single point of failure در Database singleton

`core/Database.php` از الگوی Singleton استفاده می‌کند (`Database::getInstance()`). این یعنی تمام ماژول‌ها (از جمله gateway در صورت ادغام) از یک اتصال PDO واحد استفاده می‌کنند. اگر این اتصال قطع شود، کل سیستم از کار می‌افتد. برای یکپارچه‌سازی gateway، این به‌معنای آن است که یک کندی در DB هم بر کاربر v2 و هم بر gateway اثر می‌گذارد. **پنهان:** بدون pool اتصال یا read replica، رشد ترافیک gateway می‌تواند DB را برای کاربران v2 کند کند.

## ۷. نقشهٔ راه توسعهٔ Mojavez-v2 (پیش از ادغام)

پیش از یکپارچه‌سازی با gateway، شش فاز زیرساختی باید روی v2 اجرا شود. هر فاز مستقل، قابل آزمون و قابل rollback است.

### ۷.۱. فاز ۰: تثبیت foundation

تثبیت سه پایه: نخست، **یکپارچه‌سازی نسخه** — یک منبع حقیقت (`VERSION` = `2.1.0`) که `README`, `config/config.php` (`APP_VERSION`) و `REFACTOR_PLAN` به آن ارجاع دهند. دوم، **یکپارچه‌سازی schema** — حذف `database/install.sql` و نگه‌داری فقط `schema.sql` به‌عنوان منبع حقیقت، یا تبدیل `install.sql` به alias. سوم، **runner مهاجرت** — افزودن جدول `migrations` (با `filename`, `applied_at`, `checksum`) و یک runner (الگو از MigrationRunner ماژول Scraper نسخهٔ محلی) که `database/migrations/` را اجرا و پیگیری کند.

### ۷.۲. فاز ۱: لایهٔ ماژولار

ساخت `app/Modules/` با `ModuleLoader` (بارگذاری خودکار ماژول‌ها از `app/Modules/*/manifest.php`) و `ModuleInterface` (متدهای `register()`, `boot()`, `routes()`, `migrations()`). هر ماژول فضای نام اختصاصی (`Modules\Gateway`)، کنترلر/مدل/ویوی خود و مهاجرت‌های خود را دارد. این لایه، ماژول gateway را به‌صورت ایزوله بارگذاری می‌کند بدون آنکه ساختار مسطح v2 را بشکند. قرارداد کامل در پیوست ب.

### ۷.۳. فاز ۲: لایهٔ API

ساخت یک لایهٔ API مستقل از لایهٔ وب: مسیرهای `/api/v1/*` با `ApiController` پایه (خروجی JSON استاندارد با `{success, data, error, meta}`)، نسخه‌بندی در URL، اعتبارسنجی ورودی متمرکز (JSON Schema یا کلاس `Validator` توسعه‌یافته) و rate limit سراسری. این لایه gateway را از طریق قرارداد نسخه‌دار تغذیه می‌کند.

### ۷.۴. فاز ۳: سیستم رویداد و صف

ساخت یک `EventDispatcher` ساده (الگوی pub/sub درون‌پروسه‌ای) برای شروع، به‌ضمن افزودن یک صف ماندگار (table-backed queue با `jobs` جدول + worker CLI `php scripts/worker.php`) برای عملیات غیرهم‌زمان. رویدادهایی مانند `LicenseIssued`, `PaymentConfirmed`, `ApplicantStatusChanged` منتشر می‌شوند؛ gateway (در فاز ادغام) به‌عنوان مشترک ثبت می‌شود. `AutoCancelService` نیز به صف منتقل می‌شود.

### ۷.۵. فاز ۴: لایهٔ دسترسی به داده

استخراج Interfaceهای Repository (`ApplicantRepositoryInterface`, `PaymentRepositoryInterface`) از مدل‌های فعلی، با پیاده‌سازی PDO فعلی به‌عنوان `PdoApplicantRepository`. کنترلرها و سرویس‌ها به‌جای مدل مستقیم، به Interface وابسته می‌شوند. این امکان را فراهم می‌کند که gateway از طریق Repository خوانده/نوشته شود (نه مدل concreto) و تست‌پذیری به‌شدت بالا می‌رود.

### ۷.۶. فاز ۵: CI/CD و آزمون یکپارچه‌سازی

راه‌اندازی GitHub Actions (یا معادل): روی هر push و PR، اجرای `php tests/run.php`, lint (`php -l`), static analysis و contract test. افزودن contract test‌ها: یک مجموعه از fixture‌های request/response که قرارداد API را ثبت می‌کنند. این فاز پیش‌نیاز مستقیم یکپارچه‌سازی است: بدون آن، هر تغییر می‌تواند gateway را بشکند.

## ۸. استراتژی یکپارچه‌سازی با mojavez-gateway

### ۸.۱. الگوی Anti-Corruption Layer (ACL)

توصیه: gateway به‌طور مستقیم به مدل‌ها/schema v2 متصل نشود؛ در عوض یک لایهٔ ACL (Anti-Corruption Layer) بین آن‌ها قرار گیرد. ACL یک adapter است که ترجمهٔ مدل داده، اعتبارسنجی و سوءاستفاده‌نشدن v2 توسط gateway را بر عهده می‌گیرد. اگر gateway روزی تغییر کند یا جایگزین شود، فقط ACL به‌روزرسانی می‌شود، نه v2. این الگو (از DDD) باعث می‌شود v2 در برابر تغییرات gateway مصون بماند.

### ۸.۲. قرارداد یکپارچه‌سازی نسخه‌دار

یک سند قرارداد (`docs/integration-contract.md` در مخزن جدید) که endpoint‌ها، payload‌ها، نوع‌ها، کد وضعیت‌ها و نسخه‌بندی را تعریف می‌کند. هر تغییر breaking با افزایش نسخه-major همراه است. یک schema registry (حتی به‌سادگی یک پوشه از JSON Schema‌های نسخه‌دار) به‌عنوان مرجع مشترک خدمت می‌کند. contract test‌ها (فاز ۵) این قرارداد را به‌صورت اجرایی اعمال می‌کنند.

### ۸.۳. همگام‌سازی یک‌طرفه اول، دوطرفه بعد

توصیه: یکپارچه‌سازی را در دو مرحله اجرا کنید. مرحلهٔ ۱: همگام‌سازی **یک‌طرفه خروجی** (v2 → gateway فقط خواندنی، gateway تغذیه می‌شود). این ریسک drift دوطرفه را حذف می‌کند. مرحلهٔ ۲: پس از تثبیت مرحلهٔ ۱ و با مکانیزم‌های حل تعارض (timestamp + source-of-trith)، همگام‌سازی **دوطرفه** فعال شود. این تقلیل ریسک تدریجی، از فاجعهٔ تولید جلوگیری می‌کند.

### ۸.۴. مخزن جدید: monorepo یا multi-repo

توصیه: **monorepo** برای مخزن جدید ادغام. دو گزینه وجود دارد: (الف) monorepo — v2 و gateway در یک مخزن با `apps/mojavez/` و `apps/gateway/` + `packages/shared/` (قرارداد مشترک). (ب) multi-repo — دو مخزن جدا با یک مخزن سوم برای shared kernel. monorepo مزیت: تغییرات هم‌زمان در یک commit، contract test آسان، نسخه‌بندی هماهنگ. multi-repo مزیت: استقلال deploy. با توجه به وابستگی بالای قرارداد، monorepo توصیه می‌شود.

### ۸.۵. migration مشترک و ماتریس مالکیت

در monorepo، مهاجرت‌ها در `packages/shared/migrations/` متمرکز می‌شوند، اما **ماتریس مالکیت** روشن می‌کند کدام جدول متعلق به کدام ماژول است: جداول `applicants`, `persons`, `payments` و غیره متعلق به v2 (gateway فقط می‌خواند/می‌نویسد از طریق ACL)؛ جداول `integration_log`, `gateway_ref_map` متعلق به shared kernel؛ جداول خاص gateway در `apps/gateway/migrations/`. این ماتریس از drift schema جلوگیری می‌کند.

### ۸.۶. circuit breaker و fallback

ACL باید یک circuit breaker پیاده‌سازی کند: اگر gateway سه بار پشت سر هم timeout یا خطا داد، ACL به حالت «open» می‌رود (همگام‌سازی متوقف، در صف می‌ماند) و v2 در حالت degraded (بدون gateway) ادامه می‌دهد. پس از یک دورهٔ cooldown، ACL به حالت «half-open» می‌رود و یک درخواست آزمایشی می‌فرستد؛ اگر موفق بود، به «closed» برمی‌گردد. این مکانیزم، قطع gateway را به قطع v2 تبدیل نمی‌کند.

ACL ترجمه، اعتبارسنجی و circuit breaker را بر عهده دارد. v2 توسعه‌یافته شامل چهار لایهٔ جدید است: API Layer (gateway از اینجا تغذیه می‌شود)، Module Layer (بارگذاری ایزولهٔ ماژول‌ها)، Core (منطق موجود) و Event Bus (انتشار رویداد برای gateway). Shared Kernel (قرارداد + schema registry + نسخه) بر ACL حاکم است و یک منبع حقیقت برای قرارداد فراهم می‌کند. داده در DB واحد `handicraft_license` با ۲۸ جدول موجود + جدول‌های جدید integration می‌ماند.

## ۱۰. سنجه‌های موفقیت

پس از اجرای کامل، چهار سنجه کلیدی پایش می‌شوند. نخست، **پوشش contract test**: ۱۰۰٪ endpoint‌های gateway-facing با contract test پوشش داده شوند. دوم، **در دسترس بودن**: زمان قطعی v2 ناشی از قطع gateway باید صفر باشد (circuit breaker مؤثر). سوم، **تأخیر همگام‌سازی**: تأخیر میان‌توسط از تغییر در v2 تا انعکاس در gateway زیر ۵ ثانیه (در حالت عادی) و زیر ۱ دقیقه (در حالت صف‌پر). چهارم، **یکپارچگی داده**: درصد رکوردهای ناسازگار (v2 vs gateway) زیر ۰.۱٪ با آستانهٔ هشدار خودکار. علاوه بر این، debt فنی باید در هر فاز بازبینی شود تا انباشت نداشته باشد.

## ۱۱. جمع‌بندی و توصیه‌های نهایی

Mojavez-v2 یک پایهٔ فنی خوب دارد (PHP ۸ خالص، refactor کامل، امنیت پایه) اما برای یکپارچه‌سازی با یک ماژول خارجی آماده نیست. ده حوزهٔ ساختاری نیازمند توسعه است، و دوازده جنبهٔ پنهان ریسک آینده را شکل می‌دهند. ترتیب توسعه‌دهنده درست است: «اولاً v2 توسعه کامل، ثانیاً یکپارچه‌سازی» — اما «توسعهٔ کامل» باید شامل شش فاز زیرساختی (foundation، ماژولار، API، رویداد/صف، repository، CI/CD) باشد.

سه توصیهٔ نهایی: (۱) پیش از هر چیز، فاز ۰ (تثبیت foundation) را اجرا کنید — بدون نسخه‌بندی واحد، schema یکپارچه و runner مهاجرت، بقیه-building- blocks روی پایهٔ ناپایدار می‌نشینند. (۲) یکپارچه‌سازی را یک‌طرفه شروع کنید (v2 → gateway خواندنی) و پس از تثبیت، دوطرفه کنید — این تقلیل ریسک تدریجی از فاجعهٔ تولید جلوگیری می‌کند. (۳) ACL را جدی بگیرید — این لایه، v2 را در برابر تغییرات و قطعی‌های gateway مصون می‌کند و در درازمدت از debt فنی شدید جلوگیری می‌کند. این سند تحلیلی است و هیچ تغییری در مخزن اعمال نکرده است.

## پیوست ب: قرارداد ModuleInterface پیشنهادی

```php
<?php
declare(strict_types=1);

namespace Core\Modules;

/**
 * قرارداد پایهٔ هر ماژول در app/Modules/.
 * هر ماژول این Interface را پیاده‌سازی می‌کند تا ModuleLoader آن را شناسایی کند.
 */
interface ModuleInterface
{
    /** نام یکتای ماژول (مثل 'gateway'). */
    public function name(): string;

    /** نسخهٔ ماژول (SemVer، مثل '1.0.0'). */
    public function version(): string;

    /** ثبت سرویس‌ها و وابستگی‌ها (قبل از boot). */
    public function register(ModuleLoader $loader): void;

    /** راه‌اندازی پس از ثبت همهٔ ماژول‌ها. */
    public function boot(ModuleLoader $loader): void;

    /** مسیرهای ماژول (به Router افزوده می‌شوند). */
    public function routes(): array;

    /** فهرست فایل‌های مهاجرت (نسبی به مسیر ماژول). */
    public function migrations(): array;

    /** مشترک‌های رویداد (event => handler). */
    public function subscribers(): array;
}
```

این قرارداد، قراردادی است که ماژول gateway در فاز ادغام باید پیاده‌سازی کند. `ModuleLoader` در `boot()` ماژول‌ها را بارگذاری، در `routes()` مسیرها را ثبت و در `migrations()` مهاجرت‌ها را به runner می‌سپارد.
