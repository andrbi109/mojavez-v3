# mojavez-v3 — database/

Single source of truth for the v3 database schema (resolves debt **D-2-7**).

## Files

| File | Purpose |
|---|---|
| `schema.sql` | **Canonical v3 schema** — all 41 tables, auto-generated by `scripts/generate_schema_sql.py`. Idempotent (`CREATE TABLE IF NOT EXISTS`), no `AUTO_INCREMENT=N` sample values, no `ALTER TABLE` (ALTERs from migrations are merged into the final `CREATE TABLE` shape). |
| `install.sql` | Fresh-install wrapper. Creates the `mojavez_v3` database + the `mojavez` user (idempotent), then `SOURCE schema.sql`. Run as DB root: `mariadb -u root -p < database/install.sql`. |

## How schema.sql is generated

```
python3 scripts/generate_schema_sql.py
```

The generator:

1. Collects every migration file across modules in canonical order:
   `app/Modules/Core/migrations/*.sql`,
   `app/Modules/NationalGateway/migrations/*.sql`,
   `app/Modules/Queue/migrations/*.sql`.
2. Runs `php scripts/migrate.php --all` against the configured DB (idempotent — re-runs are safe).
3. Runs `SHOW CREATE TABLE` for every table (excluding the `migrations` meta-table).
4. Converts `CREATE TABLE` → `CREATE TABLE IF NOT EXISTS` and strips `AUTO_INCREMENT=N` (sample data — schema.sql is for fresh installs).
5. Writes `database/schema.sql`.

This guarantees schema.sql matches **exactly** what the app would produce after running all migrations on a fresh DB — including ALTER TABLE merges (e.g. `national_licenses.matched_applicant_id` from migration 002_NG, `jobs.priority`+`result_count` from migration 002_Queue, `sync_audit_log.applicant_id` nullable from migration 003_NG).

## When to regenerate

- **After adding a new migration.** Run the generator so schema.sql reflects the new shape.
- **Before a release.** Verify schema.sql is in sync with the migrations (CI could check this with a diff).

## DO NOT edit schema.sql by hand

Edit the migration files in `app/Modules/<X>/migrations/` and re-run the generator. Hand-edits will be silently overwritten on the next regenerate.

## Schema ownership

Each table is owned by exactly one module — see `docs/SCHEMA_OWNERSHIP.md` for the full matrix. The owner is responsible for the migration files that create/alter that table.
